# دليل المشروع للفريق — SCEMS

هذا الملف يشرح **المشروع كامل** لأي عضو في الفريق: وش يسوي النظام، وين مكان كل متطلب في الكود،
كيف تشغّله على جهازك، وكيف تعرضه في المناقشة. اقرأه من البداية للنهاية مرة واحدة، وبعدها
استخدمه كمرجع.

> اسم المنتج: **Smart Campus Event Manager System** — نظام إدارة فعاليات الحرم الجامعي الذكي.
> نقول دائمًا **"Attendee / الحاضر"** وليس "Student".

---

## 1. النظام في دقيقة

منصة ويب لإدارة فعاليات جامعة حائل، بلغتين (العربية افتراضيًا من اليمين لليسار، والإنجليزية).
فيها ثلاثة أدوار:

| الدور | وش يسوي |
|---|---|
| **Attendee — الحاضر** | يتصفح الفعاليات ويبحث ويفلتر، يحجز مقعد ويستلم تذكرة QR، يلغي الحجز، يشوف سجل حجوزاته، يقيّم الفعالية بعد ما تنتهي، يستلم إشعارات، ويسأل المساعد الذكي. |
| **Organizer — المنظم** | يسجّل بنفسه، ينشئ فعالية (تروح للمشرف للموافقة)، يعدّل ويحذف فعالياته، يشوف المسجلين، **يسجّل الحضور عند الباب بمسح QR**، يشوف تقييمات فعالياته، ويستلم إشعار لما تكتمل المقاعد أو لما يوافق المشرف/يرفض. |
| **Admin — المشرف** | يوافق أو يرفض الفعاليات، يدير المستخدمين والفئات، يرسل إعلان لكل المستخدمين، يحذف أي فعالية، ويشوف **الإحصائيات وتوقّع الحضور**. |

### رحلة فعالية من البداية للنهاية

1. المنظم يسجّل حساب (رقم جوال إلزامي) ← يرسل طلب فعالية ← حالتها **PENDING**.
   (المنظم الجديد يقدر يرسل **طلب واحد فقط** لين يُعتمد أول طلب له.)
2. المشرف يوافق ← الفعالية **APPROVED** وتظهر للجميع، ويوصل المنظم **إشعار**.
3. الحاضر يحجز ← يستلم **تذكرة QR** + إشعار تأكيد. لو امتلأت المقاعد يوصل المنظم إشعار.
4. يوم الفعالية: المنظم يفتح **شاشة تسجيل الحضور** ويمسح التذاكر بكاميرا الجوال.
5. بعد ما تنتهي: الحاضر **يقيّم** (1–5 نجوم + تعليق)، والمنظم يشوف التقييمات.
6. المشرف يشوف كل هذا في **الإحصائيات**، مع توقّع عدد الحضور للفعاليات الجاية.

## 2. المتطلبات الوظيفية (FR) — وين كل واحد

كل الـ 23 متطلب مبنية ومختبرة. الأعمدة: الواجهة الخلفية (API) والواجهة الأمامية (الشاشة).

| FR | المتطلب | API (backend) | الشاشة (frontend) |
|---|---|---|---|
| FR-01 | التسجيل (حاضر أو منظم) | `POST /api/attendee/auth/register` | `/register` |
| FR-02 | تسجيل الدخول لكل الأدوار | `POST /api/attendee/auth/login` | `/login` |
| FR-03 | تصفح الفعاليات القادمة | `GET /api/attendee/events` | `/events` |
| FR-04 | البحث والفلترة (فئة، مكان، تاريخ) | نفس السابق مع `?category=&venue=&date=` | `/events` |
| FR-05 | حجز مقعد + تذكرة QR | `POST /api/attendee/bookings` | `/events/:id` و `/bookings` |
| FR-06 | إشعار تأكيد الحجز | يُنشأ مع الحجز | الجرس 🔔 و `/notifications` |
| FR-07 | إلغاء الحجز قبل بداية الفعالية | `POST /api/attendee/bookings/:id/cancel` | `/bookings` |
| FR-08 | سجل الحجوزات | `GET /api/attendee/bookings` | `/bookings` |
| FR-09 | تفاصيل الفعالية | `GET /api/attendee/events/:id` | `/events/:id` |
| FR-10 | إنشاء فعالية | `POST /api/organizer/events` | `/organizer/events/new` |
| FR-11 | تعديل فعالية | `PATCH /api/organizer/events/:id` | `/organizer/events/:id/edit` |
| FR-12 | حذف فعالية (بدون حجوزات) | `DELETE /api/organizer/events/:id` | `/organizer` |
| FR-13 | قواعد السعة | تُفحص في الإنشاء والتعديل | نموذج الفعالية |
| FR-14 | قائمة المسجلين + **تسجيل الحضور بـ QR** | `GET .../attendees`، `POST .../check-in` | `/organizer/events/:id/attendees` و `/check-in` |
| FR-15 | إشعار المنظم عند اكتمال المقاعد | يُنشأ مع آخر حجز | الجرس 🔔 |
| FR-16 | صورة ومرفقات الفعالية (روابط) | ضمن إنشاء/تعديل الفعالية | نموذج الفعالية |
| FR-17 | موافقة/رفض المشرف (+ إشعار للمنظم) | `POST /api/admin/events/:id/approve|reject` | `/admin/events` |
| FR-18 | إدارة المستخدمين | `/api/admin/users` | `/admin/users` |
| FR-19 | إدارة الفئات | `/api/admin/categories` | `/admin/categories` |
| FR-20 | **الإحصائيات وتوقّع الحضور** | `GET /api/admin/analytics` و `/predictions` | `/admin/analytics` |
| FR-21 | إعلان لكل المستخدمين | `POST /api/admin/broadcast` | `/admin/broadcast` |
| FR-22 | حذف نهائي لأي فعالية/مستخدم | `DELETE /api/admin/events/:id` و users | `/admin/events` و `/admin/users` |
| FR-23 | **المساعد الذكي** (Groq) | `POST /api/chatbot` | زر المحادثة الدائري في كل شاشة بعد الدخول |

**إضافات خارج قائمة الـ FR** (موثّقة لأن الشاشات تحتاجها):
- **التقييمات** بعد الفعالية: `POST /api/attendee/events/:id/feedback` و `GET /api/organizer/events/:id/feedback`.
  (شاشة التقييم موجودة في التصاميم الـ 17، لكن ما لها رقم FR — اسألوا المشرف تحت أي FR تُحسب.)
- **صندوق الإشعارات** لكل الأدوار: `GET /api/notifications` + تحديد كمقروء.
- **تسجيل المنظم بنفسه** مع حد "طلب واحد قبل أول موافقة".

التفاصيل الكاملة لكل endpoint (الأشكال، الأخطاء) في ملفات `API.md` داخل كل مجلد في
`backend/src/modules/`.

## 3. كيف مبني المشروع

```
المتصفح (Next.js على Vercel)
   │  كل الطلبات عبر frontend/lib/api.ts  (كوكي الجلسة httpOnly)
   ▼
الخادم (Express على DigitalOcean)  ──►  قاعدة البيانات (Supabase Postgres عبر Prisma)
   │                                 ──►  Groq (موديل gpt-oss-120b) للمساعد الذكي — من الخادم فقط
   └──►  خدمة التحليلات (Python FastAPI) — داخلية، لتوقّع الحضور فقط
```

- **المتصفح لا يكلّم قاعدة البيانات ولا Groq أبدًا** — كل شيء يمر بالخادم.
- كل رد من الـ API بنفس الشكل: `{ success: true, data }` أو `{ success: false, error: { message, code } }`.
  الواجهة تعرض الخطأ حسب الـ `code` مترجمًا (لا تعرض نص الخادم الإنجليزي أبدًا).
- الصلاحيات في الخادم (`requireAuth` + `requireRole`)، وليست في قاعدة البيانات.
- الوقت يُخزَّن UTC ويُعرض بتوقيت الحرم الجامعي (الرياض، UTC+3).

### المجلدات المهمة

| المسار | المحتوى |
|---|---|
| `backend/src/modules/attendee` | التسجيل والدخول، الفعاليات، الحجوزات، التقييم |
| `backend/src/modules/organizer` | فعاليات المنظم، المسجلين، تسجيل الحضور، التقييمات |
| `backend/src/modules/admin` | الموافقة، المستخدمين، الفئات، الإعلان، الحذف |
| `backend/src/modules/notifications` | صندوق الإشعارات لكل الأدوار |
| `backend/src/modules/analytics` | الإحصائيات (FR-20) ونقل طلب التوقع لخدمة Python |
| `backend/src/modules/chatbot` | المساعد الذكي (Groq) |
| `backend/prisma/schema.prisma` | جداول قاعدة البيانات (8 جداول) |
| `analytics/app/model.py` | نموذج توقّع الحضور (مشروح خطوة بخطوة في أول الملف) |
| `frontend/app/[locale]/…` | كل الشاشات، مقسّمة حسب الدور: `(attendee)`، `(organizer)`، `(admin)` |
| `frontend/components` | المكونات المشتركة (الأزرار، البطاقات، الجرس، المساعد…) |
| `frontend/messages/ar.json` و `en.json` | كل نصوص الواجهة باللغتين (نفس المفاتيح في الملفين) |

### كيف يشتغل توقّع الحضور (FR-20) — للشرح في المناقشة

1. **الطلب على المقاعد**: نتعلم من الفعاليات السابقة نسبة امتلائها (الحجوزات ÷ السعة).
   - إذا عندنا 12 فعالية سابقة أو أكثر: نموذج **Random Forest** يتعلم من الفئة، السعة، اليوم،
     الساعة، مدة الفعالية، وكم يوم قبلها أُعلنت.
   - إذا أقل: متوسط الفعاليات السابقة من **نفس الفئة** (أو كل الفعاليات). الشاشة تقول بصراحة أي طريقة استُخدمت.
2. **نسبة الحضور الفعلي**: من الفعاليات اللي استُخدم فيها تسجيل الحضور بالـ QR (80% افتراضيًا إذا ما فيه).
3. **الحضور المتوقع** = الحجوزات المتوقعة × نسبة الحضور الفعلي.

الخادم يرسل لخدمة Python **أرقام فقط** (بدون أسماء أو إيميلات أو عناوين فعاليات).

## 4. التشغيل على جهازك

المتطلبات: Node.js 20+، و Python 3.12+ (للتحليلات فقط).

1. انسخ `.env.example` إلى `.env` في جذر المشروع واطلب القيم من قائد الفريق
   (**لا ترفع `.env` أبدًا**). المتغيرات:
   `DATABASE_URL`، `DIRECT_URL`، `JWT_SECRET`، `SEED_ADMIN_EMAIL/PASSWORD`،
   `GROQ_API_KEY`، `GROQ_MODEL`، `ANALYTICS_URL` (الأخيرة اختيارية).
2. الخادم:
   ```bash
   cd backend
   npm install
   npm run dev          # http://localhost:5000/health
   ```
3. الواجهة:
   ```bash
   cd frontend
   cp .env.example .env.local
   npm install
   npm run dev          # http://localhost:3000
   ```
4. خدمة التحليلات (اختياري — بدونها كل شيء يشتغل ما عدا "الحضور المتوقع"):
   ```bash
   cd analytics
   pip install -r requirements.txt
   uvicorn app.main:app --reload --port 8000
   ```
5. بيانات تجريبية: `cd backend && npm run db:seed` (الفئات والقاعات وأول مشرف)، ثم
   `npm run db:seed:demo` (منظم تجريبي و4 فعاليات).

**تحديث قاعدة البيانات** (للمسؤول عنها فقط): `cd backend && npm run prisma:deploy` يطبّق
أي migration جديد. في هذا الفرع migration جديد واحد: إضافة نوعي إشعار
(`EVENT_APPROVED`، `EVENT_REJECTED`) — لازم يُطبَّق قبل تشغيل الموافقة/الرفض.

## 6. سيناريو العرض في المناقشة (10 دقائق تقريبًا)

حضّر ثلاثة متصفحات/نوافذ: مشرف، منظم، حاضر.

1. **الصفحة الرئيسية** بالعربي، ثم بدّل للإنجليزي (الاتجاه يتغير).
2. **منظم جديد** يسجّل من "سجّل كمنظم" ← ينشئ فعالية ← يحاول طلب ثاني (يظهر حد الطلب الواحد).
3. **المشرف** يوافق من `/admin/events` ← المنظم يشوف الجرس 🔔 فيه إشعار "تمت الموافقة".
4. **حاضر** يحجز ← تظهر تذكرة QR + إشعار تأكيد.
5. **المنظم** يفتح "مسح التذاكر" بجواله (Chrome على أندرويد) ويمسح التذكرة ← "تم تسجيل الحضور"،
   ثم يمسحها مرة ثانية ← "سُجّل حضوره مسبقًا الساعة …".
6. **المساعد الذكي**: اسأل "وش الفعاليات هذا الأسبوع؟" بالعربي ثم بالإنجليزي.
7. **المشرف** يفتح الإحصائيات: الأرقام، الرسم الشهري، الفئات، والحضور المتوقع — واشرح الطريقة (القسم 3).
8. (اختياري) فعالية منتهية: الحاضر يقيّم ← المنظم يشوف "التقييمات".

## 7. اللي باقي (يحتاج قرار أو معلومة، مو كود)

| البند | ليش |
|---|---|
| **إرجاع قاعدة البيانات** (Supabase SCEMS-eu) | المشروع متوقف (الخطة المجانية توقف المشاريع غير النشطة). بعد تشغيله: `npm run prisma:deploy` ثم `npm run db:seed:demo`. |
| **مفتاح Groq** (`GROQ_API_KEY`) | بدونه المساعد يقول "غير متاح الآن" بشكل مرتب، لكن ما يجاوب. |
| **النشر** (Vercel + DigitalOcean) | الخطوات في `docs/DEPLOY.md`. يُفضّل سيرفر في أوروبا (قريب من قاعدة البيانات في فرانكفورت) — هذا يحل بطء الحجز. |
| **مطابقة ملف الـ SRS** | الأوصاف في الجدول أعلاه مأخوذة من الكود. قارنوها بنص الـ SRS الرسمي. |
| **التوصيات الذكية** | مذكورة في المميزات في README لكن ما لها FR. إذا مطلوبة، نضيفها على نفس خدمة التحليلات. |
| **المسح على آيفون (Safari)** | Safari ما يدعم قارئ QR المدمج. البدائل الموجودة: كتابة الرمز، أو التسجيل من قائمة المسجلين. الحل الكامل يحتاج مكتبة قراءة QR (يحتاج موافقة لإضافة dependency). |
| **التسجيل بإيميل الجامعة فقط** | حاليًا أي إيميل صحيح مقبول — قرار للمشرف (README، Known limitations). |
| **تطبيق جوال** | الـ NFR يذكر React Native؛ بنينا موقع متجاوب. يحتاج موافقة المشرف كتابيًا. |
